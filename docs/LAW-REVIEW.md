# Human law-package review checklist

G-04 is a human gate: G names the reviewer. This read-only tool does not choose
that person, review law, change labels, install a package, send or publish.

From the engine repository root:

```sh
python3 -B -m campaign_tool.records law-package check jurisdictions/us-ca
```

The argument is a package **directory** containing `package.json`, named for its
jurisdiction (for example `us-ca`). The command prints the human checklist and
one row per rule; it never fetches sources or writes files.

## What the reviewer does

1. Confirm that G named you and that you are independent of the package author.
   The maintainer must verify your identity and legal-review qualifications;
   software cannot authenticate a person from a name in JSON.
2. Follow [LAW-PACKAGES.md](LAW-PACKAGES.md). Read each cited primary source;
   check the version, effective dates, actor, activity, duty, exceptions and remedy.
   Check records-law timing, source access dates and request-scope coverage too.
3. Record unresolved questions honestly. Do not promote guidance, contested
   interpretations or missing primary evidence merely to make a validator pass.
   Keep the package draft while any rule cannot properly be marked verified.
4. Only after completing the substantive review, record your actual name or
   accountable personal handle in `reviewed_by`, and its calendar date as
   `reviewed_at` (`YYYY-MM-DD`, not a future date). Never use an email address,
   credentials, a role placeholder or a model identity as the reviewer's name.
5. Before claiming `status: reviewed`, every rule must have `review: verified`,
   a non-blank citation and schema-valid sources. Run the command above against
   the proposed package, and the existing `tools/check_law_review.py OLD.json
   NEW.json` diff check on both copies as described in LAW-PACKAGES.md. Submit
   the source-by-source review record for maintainer review; this tool grants
   no merge, publication or live-install authority.

## What the output proves

- Exit **0**, `draft: 0 of N rules verified`: the draft is structurally valid,
  not human-accepted. Existing author-level `verified` labels are reported
  separately, unchanged; they do not count as package-level human verification.
- Exit **0**, `OK`: a reviewed package has the required metadata and every rule
  is labeled verified with a citation. This is **not** legal acceptance.
- Exit **2**: refused. `REVIEWER_MISSING` means names are absent, blank or obvious
  placeholders/model labels; `REVIEWER_DUPLICATE` means repeated names;
  `REVIEW_DATE_INVALID` means a missing, impossible or future date;
  `RULE_UNVERIFIED <rule_id>` and `RULE_CITATION_MISSING <rule_id>` identify
  unfinished rules. `RULES_MISSING` refuses an empty reviewed package.
  `PACKAGE_INVALID` means unreadable input, schema or canonical semantic errors.
  Schema-invalid date formats also produce `PACKAGE_INVALID`.

A non-blank name is only an assertion. A successful structural check remains
review-required: the maintainer checks human identity, independence and the
substantive source record. The normal CI-discovered test runs this same CLI on
the shipped draft package, and tests refusal/OK using synthetic fixtures.

## What may not be delegated to a model

Do not ask a model to supply the missing human reviewer, impersonate a signer,
attest that sources were personally read, resolve legal uncertainty, upgrade
review labels, or provide final legal acceptance. Mechanical formatting or
validation is not that acceptance. No legal content is generated by this tool.
Neither this command nor green CI releases G-04 or any redaction, review,
source, live-run, outbound or publication hold.
